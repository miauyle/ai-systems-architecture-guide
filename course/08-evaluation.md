# 第 8 课：从一次成功演示到可复核的系统验收

[课程目录](README.md) · [上一课](07-agent.md)

前面分别验证过预测、缓存、检索和工具执行。但一个完整助手仍可能在某个环节失败。本课把这些验证按依赖组织起来，建立能定位问题、比较版本并保留证据的评估流程。

## 1. 先写清楚成功是什么

对“上海住宿上限多少”，成功意味着使用当前组织和日期对应的制度，回答数值与单位，并且引用支持回答。对“创建超标申请”，成功意味着字段和前置条件正确、外部记录已确认、效果没有重复。

回答看起来流畅或输出了一个 ID，都不足以单独定义成功。建议每条测试保存：输入、身份/日期、预期证据、必需事实、允许动作、预期外部效果和终止状态。

一个教学测试项：

```json
{
  "case_id": "qa-a-current",
  "query": "上海住宿上限多少？",
  "org": "org-a",
  "as_of": "2026-10-01",
  "expected_evidence": ["travel-2026#hotel"],
  "required_facts": {"amount": 800, "unit": "每人每晚", "tax_included": true},
  "required_condition": "超出部分需事前审批",
  "allowed_write_effects": 0
}
```

这些字段不是凭模型回复自动生成的“标准答案”，应由可靠原文或已验证业务状态确定。测试数据中的制度依然是教学假设。

## 2. 按环节定位失败，而不是一律改 Prompt

把一次请求拆成：

```text
问题与身份
 → 有效候选集合
 → 召回与重排
 → 最终证据包
 → 模型回答或动作
 → 工具校验
 → 外部执行与对账
 → 用户结果
```

保存各阶段产物。例如回答用了 600 元：先查证据包是否包含旧制度。若包含，追到版本过滤；若证据是 800 而模型写成 600，再查生成或解析。用一个整体“错误率”不能决定应改哪个组件。

同理，重复创建两份申请可能来自服务幂等缺失，而不是模型推理不足。改模型前先用确定性策略复现相同工具序列，区分控制决策问题与执行保证问题。

## 3. 给每个指标写分子、分母和单位

假设 10 个问题都有标注的必要证据，检索 top-5 对其中 8 个包含全部必要证据。这里按问题计算的完整证据命中率是 `8/10=80%`。它不同于按块计算的 Recall，也不同于只命中任意一块的命中率。

若标注证据集合 G 中有多个必要块，按块召回率为：

```math
\mathrm{Recall@k}=\frac{|G\cap R_k|}{|G|}
```

如果两个块分别说明金额与税费，召回其中一个可得到块召回率 50%，却未必能完整回答问题。按块指标与任务完整性指标应一起看。

生成答案有四个可核验声明，其中三个得到引用支持，声明支持率为 `3/4=75%`。但若唯一不被支持的声明正好是金额，整题仍可能失败。不能只用平均支持率遮盖关键事实错误。

Agent 任务要记录完成率、确认的写效果数、重复效果、结果未知是否收敛，以及工具调用和预算。预算内停止是终止性质，不意味着任务成功。

性能指标沿第五课的时间线定义：输入/输出 Token 数、TTFT、Token 间延迟、端到端延迟、吞吐与尾部分位数。质量与性能分别测量，再按业务目标判断取舍。

## 4. 最小测试集应主动覆盖容易断裂的条件

| 测试 | 输入或注入条件 | 预期性质 | 对应位置 |
| --- | --- | --- | --- |
| 当前制度 | A、2026 年、上海住宿 | 2026 住宿块排在餐费前，回答单位完整 | 检索与生成 |
| 版本边界 | 日期恰为 2026-01-01 | 旧版本不可见，新版本可见 | 有效区间 |
| 其他组织 | B 的条款匹配词更多 | A 的候选不包含 B 条款 | 身份过滤 |
| 无候选 | 不存在的组织 | 不编造当前有效证据 | 检索与回答 |
| 输出单位错误 | 800 元被写成每天 | 即使引用正确仍判不合格 | 声明核验 |
| 回包丢失 | 服务已写入后超时 | 对账找回同一回执，写效果仍为 1 | 恢复与幂等 |
| 重复决策 | 策略持续读取制度 | 在明确预算处终止，状态可解释 | 运行时预算 |
| 错误工具参数 | 缺字段或类型错误 | 不产生外部写效果 | 契约校验 |

不必把所有测试都调用昂贵模型。版本过滤、回执映射、幂等、预算等性质先用确定性输入验证。涉及语言理解和生成的性质，再使用实际模型和独立样本。

当前示例已经执行部分机械性质；它们没有评测真实 LLM 的回答质量。单位错误测试在接入生成层后才有完整对象，不能把文档中的预期结果写成已执行成绩。

## 5. 验证模型计算时需要另一个层次的测试

第二、三课检查解析梯度是否与中心差分一致；第四、五课检查完整与缓存 logits 等价；改变未来 Token 不影响早期 logits。它们检验的是计算实现。

人工上下文任务再检查未见前缀、输入干预和理论基线。若完整计算与缓存等价，却预测错答案，可能是模型没有学会；若学会了训练样本但缓存推理出错，则可能是实现问题。

这些测试分层后，才能避免把训练失败归因于服务，或把服务错误误当作模型质量问题。

## 6. 比较两个版本必须逐题配对

假设旧系统在 200 题中答对 160，新系统答对 169，表面提升 4.5 个百分点。逐题比较可能发现：新系统修复 12 题，同时把旧系统答对的 3 题改错，总净增 9 题。

保存这 15 个变化的具体 ID，检查是否集中在版本切换、同义问法或单位提取等子集。只看两个总分会丢失退化位置。

测试问题来自相同场景或同一文档时，结果可能相关；样本数不等于独立证据数。可以按文档、用户或任务来源分组，并针对实际抽样单位做统计分析。

若反复用同一测试集调 Prompt，它逐渐变成开发集。最终验收需要保留未参与调参的数据，记录模型、提示、检索、文档版本和随机策略。

## 7. 小样本不能证明极低失败概率

10 次超时恢复都没有重复创建，只能说明这 10 次覆盖的条件通过。它不能证明重复概率为零，更不能证明跨进程崩溃、并发重试和真实数据库事务都正确。

一个常用近似是：在独立同分布的 n 次试验中观察到零失败，失败率的单侧 95% 上界约为 `3/n`。n=100 时仍约为 3%，不是 0%。这个近似依赖假设，不替代适当的精确区间或更丰富的故障测试。

实际恢复机制更应检查不变量：同一 operation_id 最多产生一次业务效果；已确认回执不被未验证摘要覆盖；结果未知不会被凭空宣告成功。统计样本与结构保证回答不同问题。

## 8. 模型裁判怎样使用才可复核

精确字段如金额、版本、单位、工具 ID 和写效果数，优先使用程序或人工标准检查。开放式回答的完整性和表达可用模型裁判辅助，但要给出评分标准、支持证据和逐项解释。

抽取一部分样本让人工双评，检查裁判是否偏好冗长回答、是否受答案顺序影响、是否把引用存在误判为事实受支持。记录裁判模型与提示版本。裁判意见不是不可复核的真值。

## 9. 完成一次验收的具体产物

1. 固定一份测试集及其标注依据。
2. 记录待测版本：模型、代码提交、文档索引、配置与运行环境。
3. 执行计算与运行时性质检查，再执行实际任务测试。
4. 保存每题的阶段产物、结果、失败环节和成本。
5. 与基线逐题比较，归纳改进与退化。
6. 对尚未覆盖的条件明确保留结论边界，不把单次演示写成生产验收。

运行仓库示例时，可使用[评估记录模板](../templates/evaluation-record.md)记录对应性质。文档维护另外运行 `python tools/check_docs.py`；公式修改需真实浏览器排版验证，源码检查不是数学显示结果。

## 10. 练习与解析

**练习 1。** 召回正确条款，回答金额正确，但单位写错，应把它算检索错误还是生成错误？

**解析。** 若证据包包含正确单位，属于生成或后处理错误；若切块遗漏单位，属于证据组织问题。先查看中间产物再归类。

**练习 2。** 新系统工具调用更多、成功率更高，是否必然更好？

**解析。** 需要比较成本、延迟、目标与失败后果，并定位额外调用是否有用。质量、成本和预算共同决定是否接受改动。

**练习 3。** 四层分别应该有什么验收对象？

**解析。** 模型计算看形状、因果性和数值等价；训练看梯度、标签、数据划分与独立任务；推理服务看缓存、容量、延迟与吞吐；应用看证据、身份、业务状态、工具结果和整体目标。

完成课程后，回到[专题导航](../README.md)深化 RoPE、GQA、MoE、分布式、规划、记忆与多模态。你现在应能沿“输入信息 → 可学习计算 → 训练信号 → 推理执行 → 外部证据 → 外部行动 → 验收”解释每一项技术在哪里发挥作用，而不是仅识别它的名称。深入评估见[生产验收专题](../docs/22-evaluation-and-production.md)。
