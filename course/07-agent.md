# 第 7 课：从回答到行动，构建能恢复的 Agent

[课程目录](README.md) · [上一课](06-retrieval.md) · [下一课：评估](08-evaluation.md)

用户已经知道住宿上限，接着说：“这次超标了，帮我提交申请。”问题从生成文字变成改变外部系统状态。模型可以建议下一步，但业务执行需要参数、权限、状态与结果记录共同约束。

## 1. 先把任务变成有条件的动作序列

一个合理的依赖关系是：

```text
确认用户目标与身份
  → 读取当前制度
  → 获取申请所需字段和依据
  → 校验资格、必填项与适用规则
  → 创建申请
  → 检查业务回执
  → 报告实际结果
```

如果工具只创建申请，不代表审批已通过。用户要求的最终状态、工具实际承诺的状态和助手汇报的状态必须一致。

固定工作流可以直接编写上述节点；Agent 让模型根据观测选择下一动作；两者也可结合，让模型选择路线、程序执行有约束的节点。判断差异时看控制流是谁决定的，而不是是否使用聊天界面。

## 2. 工具契约让“建议”成为可检查的调用

示意工具 `create_application` 需要：

```json
{
  "trip_id": "TRIP-DEMO-001",
  "requested_amount": 950,
  "currency": "CNY",
  "reason": "示例原因",
  "policy_evidence_id": "travel-2026#hotel"
}
```

950 元等业务数据是教学假设。契约应说明字段类型、范围、必填性、动作效果与回执含义。一个参数符合 JSON Schema，只证明形状合规；不能证明金额真实、员工有权提交、证据版本有效或申请不重复。

应用按顺序做四类检查：

1. **结构**：工具名存在，字段类型和必填项正确，无未支持字段。
2. **权限**：调用主体来自认证状态，有权访问该出差单。
3. **业务前置条件**：制度证据有效，金额单位正确，申请处于允许状态。
4. **执行策略**：步骤、调用、时间和成本预算足够；需要审批的流程已满足其规则。

工具适配器在通过检查后执行调用。模型输出一个字符串“已完成”，不能绕过这些条件，也不能直接设置应用的 `completed=true`。

## 3. 区分模型上下文与持久业务状态

模型上下文里可以有用户描述、候选证据、最近几次工具结果。持久状态保存目标 ID、已确认字段、制度版本、计划节点状态、待执行操作 ID、回执与预算。

```json
{
  "goal_id": "GOAL-DEMO-001",
  "status": "executing",
  "evidence_id": "travel-2026#hotel",
  "operation_id": "OP-DEMO-001",
  "operation_status": "pending",
  "receipt": null,
  "remaining_tool_calls": 3
}
```

聊天摘要可以说“准备提交”，但不能代替上面的状态。摘要丢掉金额、证据版本或操作 ID，可能改变下一步动作；恢复时必须以可信结构化状态为依据。

工作记忆保存当前任务信息；长期记忆可保存有来源的用户偏好或历史经验。两者都需要作用域、更新时间和失效机制。某次上海制度的 800 元不能永久写成所有地区的通用规则。

## 4. 最难的一种超时：已经写入，但回包丢了

按时间线观察：

```text
t0 应用记录操作 OP-001 为 pending
t1 工具服务收到创建请求
t2 服务创建申请 APP-001
t3 网络响应丢失
t4 应用等待超时
```

应用知道“没有收到结果”，却不知道“没有创建”。这个状态称为结果未知。直接重试一个新的创建请求可能生成第二份申请；直接说失败也不符合已发生的实际状态。

可恢复状态机为：

```text
pending → succeeded
pending → known_failed
pending → outcome_unknown → 查询 / 对账 → succeeded 或已确认失败
```

结果未知不应自动变成成功或失败。可使用稳定操作标识查询服务；如果服务暂时无法确认，保留待对账状态，并明确汇报尚未确认。

## 5. 幂等性如何让重复调用只产生一次效果

幂等键表示一次业务操作的身份。相同操作的网络重试使用相同键，服务检查这个键是否已经执行过，若执行过则返回已有结果。

“每次模型调用生成一个新 UUID”不能为重试提供稳定身份。键应与已持久化的任务/操作绑定；两次不同的用户申请应有不同操作身份，不能仅按相同金额和标题去重。

服务侧需要将幂等键记录与业务写入以合适的事务或一致性机制连接。若先创建申请、随后记录键，中间崩溃仍可能导致重试重复。内存字典只能演示语义，不能提供跨进程崩溃的可靠性。

## 6. 运行一个故意丢回包的执行循环

```bash
python examples/agent_runtime.py
```

程序创建的是模拟咨询工单，标题为“示例出差咨询”；没有真的提交差旅超标申请。它保留相同控制问题，但简化金额、身份认证、制度检索和持久存储。

策略是确定性的：无证据则读制度，无回执则创建工单，有回执则完成。实际 Agent 可以用 LLM 替换策略，输出仍经过相同校验和预算检查。

本次执行的事件链是：

```text
evidence
operation_pending
outcome_unknown
operation_verified
completed
```

服务第一次创建后故意抛超时。运行时按同一键进行只读对账，找回 `DEMO-1`；实际创建次数为 1。重复相同键，仍返回同一回执。程序同时检查无权限主体、错误动作结构和无进展循环。

步骤数为 3：读制度、创建工单、完成。工具调用数也为 3：读制度、创建、对账；完成是内部状态转换，不调用外部服务。记录指标时要说明计数口径。

## 7. 规划、重规划与记忆怎样接到执行状态

假设计划节点为 A 读取制度、B 获取行程、C 创建申请，C 依赖 A 与 B。A 完成后制度版本更新，原证据失效，C 就不能沿旧前置条件执行。重规划应使依赖旧证据的节点失效并重新校验，而不是只在聊天里加一句“制度更新了”。

计划可以表示为依赖图，每个节点保存输入来源、前置条件、状态和输出 ID。执行前检查依赖是否成功且仍有效。遇到无关的工具错误，只重试受影响节点；遇到前置事实变化，再重建相关计划。

经验记忆可以记录“上次服务超时后按 operation_id 对账”，帮助选择处理策略；事务是否完成仍应读取业务记录，不能按相似案例猜。

多个 Agent 分工检索、规划或验证时，也需要明确共享状态和唯一执行入口。多一个角色不自动增加可靠性；若两个执行者都创建申请，反而扩大重复风险。MCP 提供工具连接与描述机制，不代替应用的业务授权、幂等和恢复策略。

## 8. 预算和终止必须由运行时保证

如果模型一直重新读取相同条款，语言输出可能流畅，但任务没有进展。运行时设置最大步骤、工具调用、时间或费用，并检查连续无进展、重复动作和目标已完成。

达到预算时将任务转为未完成或需要处理，保留已确认状态。让模型自行承诺“我会在四步内结束”不构成程序保证。

成功终止条件不是模型说“完成”，而是有符合目标的可验证结果。创建申请任务可要求已确认申请 ID；审批通过任务还需审批结果，两者不能混同。

## 9. 练习与解析

**练习 1。** 创建工具超时，服务没有按操作 ID 查询的接口，可以立刻使用新键重试吗？

**解析。** 不能假设安全。先看服务是否支持同一幂等键重试及其保证；否则保留结果未知并通过可用渠道对账。没有对应机制时不能宣称自动恢复已解决。

**练习 2。** 工具返回 `{"status":"accepted"}`，助手说“审批通过”，错在哪里？

**解析。** 接受请求不等于审批通过。状态映射必须依据工具契约；即使网络成功，业务状态仍可能等待处理。

**练习 3。** 聊天摘要说上次申请失败，持久状态里存在已确认回执，应信哪个？

**解析。** 根据业务回执及其当前状态恢复。摘要用于语言上下文，不覆盖已验证的事务事实；需要对摘要错误进行修正。
