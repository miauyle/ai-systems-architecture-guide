# 第 5 课：从下一 Token 到一段回答，再到多人并发

[课程目录](README.md) · [上一课](04-decoder-and-training.md) · [下一课：检索](06-retrieval.md)

上一课得到每个位置的词表评分。本课先跟踪单个请求的生成，再计算它占用的缓存和时间，最后理解多个请求为何需要调度。数字例子是显式配置的教学估算，不是实际 GPU 基准。

## 1. 回答是怎样一小步一小步生成的

用户输入“上海住宿上限多少”，应用将角色与问题编码成 Token 前缀。模型处理前缀，取最后一个位置的 logits，得到下一 Token 分布。选出一个 Token，把它追加到前缀，再预测下一个，直到遇到结束标记、长度上限或系统终止条件。

```text
前缀 → 分布 → 选“每”
前缀+“每” → 分布 → 选“人”
前缀+“每人” → 分布 → 选“每”
… → 结束标记
```

这里按字符展示，真实 Token 可能包含多个字符。模型也不会在第一步保证之后整段答案都正确；后续输出仍由每次条件预测共同形成。

Greedy 选最大概率；温度采样先把 logits 除以温度 τ：

```math
p_i=\frac{\exp(z_i/\tau)}{\sum_j\exp(z_j/\tau)}
```

较低温度通常使分布更集中，但不能把错误知识变成正确知识。τ=0 不能直接代入公式，实际实现一般将其作为贪心解码分支。Top-p 选择累计概率达到阈值的候选集合，再归一化采样；温度与 Top-p 的具体顺序需要查看实现。

## 2. 为什么可以缓存已有位置的 K/V

在因果 Decoder 中，旧位置不能读取新加入的未来位置。只要参数、位置规则、可见历史等条件保持一致，旧位置的各层表示不会因为新 Token 到来而改变，所以它们的 K/V 可以复用。

第一次计算前缀称为 prefill，它处理许多位置，建立每层 K/V。之后每一步 decode 只计算新位置的 Query、Key、Value，把新 K/V 接到缓存中，再让新 Query 读取所有历史 Key/Value。

缓存的是每层 K/V，不是最终答案，也不是模型参数。旧 Query 通常无需缓存，因为之后只要计算新位置的输出。对双向 Attention 或改变旧前缀的场景，上述复用论证不自动成立。

跟踪四个输入位置：

| 步骤 | 本次输入位置 | 读取的历史长度 | 步骤完成后缓存位置数 |
| --- | --- | --- | --- |
| prefill | 0、1、2 | 1、2、3 | 3 |
| decode | 3 | 4 | 4 |
| decode | 4 | 5 | 5 |

绝对位置必须接着计数。若每次 decode 都将新位置编号为 0，缓存内容虽存在，位置语义却错了。运行完整 Decoder 示例中的全量/缓存对比，可以检查这个问题。

## 3. 手算一条请求的 KV 内存

设层数 L，K/V 头数 hkv，每头维度 dh，已缓存位置 T，元素字节数 s。单条请求的理论缓存为：

```math
M_{\mathrm{KV}}=2Lh_{\mathrm{kv}}d_hTs
```

前面的 2 表示 Key 与 Value 两份。假设 `L=32,hkv=8,dh=128,s=2`，每个位置占用：

```text
2×32×8×128×2 = 131,072 字节 = 128 KiB
```

4096 个位置占 `512 MiB`；16384 个位置占 `2 GiB`。再加输入和输出位置，缓存都会增长。GQA 例子中 hkv=8；若改为 32 个 K/V 头，容量是四倍。

假设 GPU 真正可用于 KV 的预算为 `8 GiB`，理论总容量是 `8 GiB / 128 KiB = 65,536` 个位置。若每条请求最终保留 4096 个位置，理论上可装 16 条。分页碎片、预留输出、暂存和运行时开销都会降低可用值。

这是总缓存位置容量，不是每秒生成 Token 数，也不是必然能达到的并发数。若单卡同时要放权重，应先从总显存减去权重和其他预算，再计算 KV。

## 4. 缓存省掉计算，为什么长上下文仍然昂贵

Prefill 对很多位置进行投影与矩阵乘法，能较好利用大矩阵并行；注意力还包含位置之间的交互。Decode 每步只有少量新位置，但仍需读取长历史 K/V，并执行各层权重投影。

所以缓存避免重复计算历史表示，并没有消除对历史缓存的访问。上下文越长，读缓存的工作越多；并发越高，活跃缓存总量也越大。

对 70 亿参数 BF16 权重，理论字节数约为 `14 GB`。在假设有效带宽为 `900 GB/s`、每步必须读取一次全部权重且没有有效跨请求摊销的简化模型中，仅权重访问下界约 `14/900=15.6 ms`。这不是模型延迟预测：实际还有 KV、算子、通信、缓存命中和 batch 摊销。

Roofline 分析比较计算量/峰值算力与访问量/有效带宽；哪一个更大，说明哪种资源更可能限制执行。不能只看到 GPU 算力数字就估计 Token 吞吐。

## 5. 调度为什么会改变用户体验

两个请求同时到来：A 的输入很长，B 只需一句短回答。若把 A 的整个 prefill 一次执行，B 的 decode 可能等待很久。分块 prefill 将 A 拆成较小片段，调度器在片段之间安排其他工作，降低阻塞但增加调度复杂度。

Continuous batching 每轮加入新请求、移除完成请求，让活跃 batch 持续变化。固定 batch 等所有成员完成，短请求退出后可能浪费空间；持续批处理提高利用率，同时需要管理不同长度的缓存和终止状态。

Paged KV 用固定大小物理块存储，逻辑序列通过块表映射，减少必须一次分配连续大缓存的压力。块大小影响碎片和管理成本；“分页”不意味着缓存可以不占显存。

Prefix cache 复用相同前缀的计算。缓存键必须覆盖模型版本、适配器、Token 序列、位置与有关计算配置；应用权限仍需单独保证，命中同一技术前缀不等于两个用户可以共享私有文档。

## 6. 性能指标必须对齐同一条时间线

```text
t0 接收请求
t1 开始执行
t2 输出首 Token
t3 输出第二 Token
…
t_end 完成
```

- 排队时间：t1−t0。
- 首 Token 延迟 TTFT：从约定起点到 t2，应声明是否包含网络与排队。
- Token 间延迟：相邻输出 Token 的时间差。
- 端到端延迟：t_end−t0。
- 吞吐：固定时间窗口内完成的请求数或输出 Token 数；二者必须分别标记。

一个服务可以提高总吞吐，同时让每个用户等待更久。评估要记录输入/输出长度分布、并发或到达率、硬件、模型配置及分位数。只报告平均值会掩盖尾部等待。

## 7. 练习与解析

**练习 1。** 上述 KV 配置中，三条请求缓存位置分别为 1024、2048、4096，理论共占多少？

**解析。** 共 7168 个位置，乘 128 KiB，得到 `896 MiB`。不同长度应按实际总位置相加，不能全部按最长长度计算；固定补齐存储可能另有浪费。

**练习 2。** 将权重量化到一半字节，KV 一定减半吗？

**解析。** 不一定。权重精度与 KV 精度是独立配置，还会涉及缩放信息及算子支持。只有明确 KV 也采用相应压缩时，才重新估算缓存字节数。

**练习 3。** 完整前缀和缓存计算 logits 不一致，应先检查什么？

**解析。** 检查位置偏移、掩码边界、各层缓存连接顺序、头维 reshape、模型是否处于相同状态以及输入是否一致。先在小模型逐层对照，再考虑浮点误差；巨大误差不能笼统归为精度不同。
