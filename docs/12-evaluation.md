# 12 · 评估、观测与可靠性

[返回目录](../README.md) · [下一章](13-multimodal-and-reasoning.md)

## 从「看着不错」到可检验

评估先定义什么叫成功，再选择指标。一个会写流畅段落的模型可能在查制度、计算金额或引用来源时频繁出错。

建立来自真实任务的测试集，记录输入、身份、允许数据、期望事实、证据和评分标准。将开发调参集与最终留出测试集分开，避免反复调参造成虚假的提升。

## 分层评估

| 层 | 要回答的问题 | 指标示例 |
| --- | --- | --- |
| 基础模型 | 能否理解和完成任务？ | 准确率、交叉熵/困惑度、代码测试通过率 |
| 检索 | 正确证据是否被找回？ | Recall@k、MRR、nDCG，视标签设计选用 |
| 生成 | 回答是否正确且有依据？ | 事实正确率、证据支持率、引用覆盖与正确率 |
| 工具 / Agent | 行动是否正确并完成目标？ | 任务成功率、调用正确率、步骤数、重复动作率 |
| 服务 | 性能和可靠性是否达标？ | TTFT、P95、吞吐、错误率、资源使用 |
| 产品 | 用户任务是否真正完成？ | 业务验收、人工修订率、每成功任务成本 |

不同模型的 Tokenizer 不同，原始 perplexity 不宜随意横向比较。公开榜单也不等于你的任务验收结果。

## 一个小型评估集怎么设计？

入门可从几十个精心标注的案例开始，用于发现问题；这不保证统计代表性。至少覆盖：

- 可直接回答、需要多段证据和需要版本判断的问题。
- 信息不存在、问题模糊和前提错误的问题。
- 无权限文档、恶意外部指令和工具失败。
- 长输入、长输出、多轮澄清和高并发。

记录模型版本、Prompt 版本、检索配置、数据快照、解码参数和运行时间。无法追踪这些信息，很难解释指标波动。

## 人工评分与模型裁判

人工评分要有明确量规，比如「结论正确且每个关键断言有证据」。先校准评分者，再检查分歧。

模型裁判可以扩展覆盖，但会受到风格偏好、顺序、模型同源性等影响。用人工标注校准，并避免让同一模型的自信表达直接充当真实性依据。

## 用失败类型定位改动

| 现象 | 优先检查 | 可能改动 |
| --- | --- | --- |
| 没有正确证据 | 解析、权限、索引、查询 | 修正分块、混合检索或元数据 |
| 有证据但结论错误 | 证据组织、指令、模型能力 | 调整上下文、Prompt 或模型 |
| 答案正确但来源不支持 | 引用绑定与断言检查 | 要求来源 ID，逐断言验证 |
| 多步过程停不下来 | 状态、终止和预算 | 限制步骤、调整控制流 |
| 首 Token 慢 | 分段链路计时 | 降排队、优化检索/prefill |
| 并发下频繁失败 | 缓存容量、调度、限流 | 控制活跃 Token、扩副本 |

## 线上观测

用 trace ID 串联检索、模型和工具调用；记录阶段耗时、Token 用量、缓存命中、错误类型和版本。需要保存业务文本时，应明确权限、脱敏与保留策略。

模型自报「90% 确信」通常不是校准后的错误概率。可靠回退应依据证据是否存在、验证是否通过和任务规则等可检查信号。

改动后先运行回归集，再按业务需要逐步放量。涉及模型输出和数据分布变化时，要评估收益与回退能力。

## 进一步：指标、统计和故障验收

不要只报告「准确率」。任务、断言、引用和工具轨迹有不同分母；检索命中一个文档，也可能缺少另一个必要条款。小测试集的高分需要结合不确定性和覆盖范围解释。

可复核样例、指标定义、Wilson 区间、配对比较、模型裁判校准、故障注入和生产验收见[第 22 章](22-evaluation-and-production.md)。
