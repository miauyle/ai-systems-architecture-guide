# 09 · 推理、KV Cache 与资源管理

[返回目录](../README.md) · [下一章](10-serving-and-distributed.md)

## Prefill 与 Decode

**Prefill** 处理已有输入序列，通常可并行计算各输入位置，建立各层的 KV Cache，并得到第一个输出 Token 所需的 logits。

**Decode** 随后逐步处理新增 Token，读取过去的 K/V，再产生下一个 Token 的 logits。单个请求各生成步骤存在依赖，但不同请求可以批处理。

```text
输入： [已有的很多 Token] ── prefill ──> 第一个输出 Token
之后： [一个新增 Token]   ── decode  ──> 下一个 Token
之后： [一个新增 Token]   ── decode  ──> 下一个 Token ...
```

首 Token 延迟包含排队、输入处理、计算和传输，不能全算成 prefill。常见逐 Token 生成速度也受到并发和调度影响。

## KV Cache 缓存了什么？

对普通因果 Transformer，每层保存已处理位置的 Key 和 Value。未来查询需要读取它们。通常不缓存全部旧 Query，因为未来位置不会拿旧 Query 重新发起注意力。

它减少重复计算，但不存储完整答案，也不改变参数。缓存会随序列长度和活跃请求数增长。

## 显存分成几笔账

```math
\text{推理显存}\approx\text{权重}+\text{KV Cache}+\text{激活/工作区}+\text{运行时开销}
```


还应预留调度、通信、内存碎片或分块利用不完全等影响。权重放得下，是必要条件之一，不是能稳定服务的充分条件。

本章统一用 **GiB = $`2^{30}`$ 字节**；十进制 GB = $`10^9`$ 字节。厂商标称、驱动显示和工具统计可能采用不同单位。

## 为什么长上下文更贵？

普通全注意力 prefill 的注意力算术量随 $`T^2`$ 增长，线性投影和 FFN 也有各自成本；总成本不能只用一个 $`T^2`$ 概括。

带 KV Cache 的单步 decode，要让新增查询访问长度为 $`T`$ 的历史，注意力部分随历史长度增长；权重读取、FFN、调度也可能占据大量时间。

小批次 decode 常受内存带宽限制，较大的批次可能提高计算利用率。实际瓶颈需测量，不能只看 GPU 理论算力。

## 如何选 Token？

- Greedy：选择最高分 Token，简单但不保证全序列最优。
- Temperature：用 $`z/\tau`$ 调整采样分布的尖锐程度，$`\tau>0`$；温度 0 通常是 API 对确定性选取的约定。
- Top-k / Top-p：截断候选集合后重新归一化采样。
- 停止条件：EOS、长度上限或应用指定边界。

低温度减少采样随机性，不是事实校验器；并行数值实现等因素也可能影响完全复现。

## 从资源增长到运行时

缓存应按所有活跃序列的实际长度求和，并考虑分块占用与输出增长。模型接收一个请求时，最好已经知道是否能满足其长度预算，而不是到最后几个 Token 才因内存不足失败。

理论缓存公式不包含块表、碎片和执行工作区。量化也可能只作用于权重；是否量化 KV 应单独检查缓存格式与算子支持。

实际计算、活跃 Token 容量、分块缓存、调度、带宽下界、量化与推测解码的机制见[第 18 章](18-inference-engineering.md)。

## 生成过程并不修改权重

一次请求先将已知输入经过网络，得到候选分布，选定输出后把它作为后续输入。权重保持不变，新增的是上下文与每层状态。

第一个输出 Token 通常来自 Prefill 的末端 logits；之后把已经选出的 Token 送回网络，得到再下一个候选。服务是否把首步也称为 Decode 属于实现命名，讨论性能时应说明边界。

历史 K/V 可复用，因为标准因果模型的旧位置表示不受未来新增 Token 影响。编辑旧前缀、切换适配器或改变位置规则后，复用条件不再自动成立。

## 不同资源随什么增长

权重主要随模型总参数与格式变化，对普通只读副本不随当前请求数直接翻倍。KV 随活跃序列长度、层与 K/V 表示增长；激活和工作区随批次、算子与长度形态变化。

训练还保存梯度、优化器与反向所需状态，因此“推理能放下”不证明“训练也能放下”。MoE 权重包括全部专家，激活量较小并不等于总存储较小。压缩缓存或滑窗结构需要按实际状态计算，不能套用普通全注意力结论。

显存耗尽可能出现在加载时、Prefill 峰值或生成后期。只看进程启动成功容易漏掉后两种，容量判断必须包括输出增长和工作区余量。

## 采样与任务目标

Greedy 选择当前最高分，采样保留分布多样性，束搜索维护多个序列候选。不同任务对多样性和精确性有不同要求，某个策略不会在所有生成任务上最好。

Top-k 与 Top-p 会改变候选集合，温度改变评分尺度。降低随机性可以减少表达波动，却不能验证事实。重复惩罚和长度处理也可能影响代码、数字和引用等任务，不能只按文风判断解码质量。

结构化约束可以限制可输出的 Token，使 JSON 或语法更容易满足格式，但仍不能证明字段值真实、业务条件正确或动作获授权。

## 长上下文与长输出的不同代价

长输入增加 Prefill 工作与初始状态，长输出增加生成步骤并继续扩大历史。多轮聊天反复提交完整历史时，前缀复用能省去部分重复计算，但不等于不占缓存。

用户看到的总时间还包含检索、工具、排队和网络。第一 Token 出得快而最终任务很慢，可能因为输出长、工具多或反复验证；只优化首字不能代表整个任务改善。
