# 19 · 检索系统：从文档到可引用证据

[返回目录](../README.md) · [RAG 基础](11-rag-and-agents.md) · [下一章](20-agent-runtime.md)

## 把检索看作独立系统

生成模型只能依据提供给它的信息作答。检索的输入是问题、上下文和用户身份，输出是经过权限与版本检查、能支持结论的证据集合。

先检索正确文档，再组织有用片段，再检查证据能否回答问题。这三个成功条件不同，应分别测量。

## 资料对象需要哪些字段？

```json
{
  "document_id": "travel-policy",
  "version": "2026-10",
  "chunk_id": "travel-policy:2026-10:section-4:chunk-2",
  "section": "住宿报销",
  "effective_from": "2026-10-01",
  "effective_to": null,
  "region": "华东",
  "acl": ["employee"],
  "source_location": "第4节，第2页",
  "text": "正文及其适用条件。"
}
```

稳定 ID 用于引用与追踪，版本与生效范围用于事实选择，ACL 用于授权。索引更新时，如果只替换向量却没同步元数据，会出现「内容新、权限旧」等一致性错误。

该结构说明数据契约；正文、日期和角色来自实际文档及授权系统。

## 分块为什么不是固定切 500 字？

固定长度可以作为基线，但条款常包含标题、前提、主体、例外和表格。若只保留「上限 500 元」，却丢掉「一线城市、指定职级」，片段语义不完整。

可优先按文档结构分段，再根据 Token 上限组合。为片段补充必要标题路径；对跨页表格保留列名、单位和注释。重叠有助于边界信息，但会造成候选重复。

可采用父子块：较小子块参与召回，命中后读取较完整父段作为上下文。这样将检索粒度与回答所需上下文粒度分开。

## 关键词检索的分数含义

BM25 结合词频、逆文档频率和长度归一化。直觉是：关键词在文档中多次出现有帮助，但收益饱和；在许多文档里普遍出现的词区分度较低。

它尤其适合制度编号、商品型号和精确名称。分词策略、大小写、别名、停用词和字段权重都会影响效果，不能只调整 top-k。

## 向量相似度并不自动等于回答价值

余弦相似度比较向量方向，点积还受向量长度影响；归一化向量后两者的排序关系才可相应简化。距离类型必须与 Embedding 模型的训练和使用约定匹配。

一个片段可能在主题上相似，却没有包含所问的具体金额。语义召回需要任务评估，而不是把高相似度直接解释为「答案正确概率」。

## ANN 索引与精确检索

当向量很多时，近似最近邻减少搜索成本，但可能漏掉真正最近项。HNSW 使用图结构；邻接规模、构建搜索宽度和查询搜索宽度影响内存、构建成本、召回与延迟。

索引层的 ANN Recall，衡量是否接近精确向量搜索结果；业务证据 Recall，衡量是否找到正确答案资料。前者很高也不能保证后者高，因为 Embedding 本身可能排错。

先用小数据集的精确检索建立参考，再判断近似搜索引入了多少额外损失。

## 过滤应该放在哪里？

权限约束必须在资料进入模型之前生效。先向量召回再过滤，容易使授权候选不足；检索过程中直接约束或扩大候选再严格过滤，需要结合索引支持与评估。

即便检索已经过滤，打开引用来源和调用业务工具仍应再次执行各自的访问控制。索引中的 ACL 不是所有后端资源的唯一授权机制。

对时间条件，应区分「最新上传」和「查询日期有效」。出差日期在未来时，适用的可能是未来生效版本，而不是今天最新的有效版本。

## 重排到底解决什么？

Cross-encoder 类重排器同时读问题和候选片段，能更细致判断关系，通常比单向量比较更昂贵。它只能重排已经召回的内容，无法修复候选中完全没有正确文档的问题。

可以用较大的廉价候选集，重排后只保留较小证据集。测量同时包含召回上限、重排收益和在线开销。

## 证据打包不是全部拼接

先去除重复和无关段落，再保留足够的条件、定义和例外。记录每个来源 ID 与文本边界，使模型能引用具体出处。

上下文有预算时，不应简单保留最前面的若干 Token：可能恰好删掉最后的例外条款。可以按证据优先级与完整语义单位选择内容，必要时先澄清问题。

多文档存在冲突时，应保留并标明版本和适用范围，让回答解释冲突或请求澄清，而不是让模型随机选一个数字。

## 引用怎样绑定到结论？

建议将回答拆成关键断言与来源 ID，例如：

```json
{
  "claims": [
    {"text": "该条款适用于所选地区和日期。", "source_ids": ["chunk-id"]}
  ],
  "missing_information": ["员工职级"]
}
```

程序先检查 ID 是否属于当前授权证据，再检查来源是否支持断言。后一项可结合人工、规则或校准后的模型裁判，不能用 ID 存在代替语义支持。

## 分层排错

| 问题 | 应检查的层 |
| --- | --- |
| 正确段落没有被解析出来 | 数据抽取与文档结构 |
| 精确向量搜索都找不到 | 查询、Embedding 与分块 |
| 精确能找到，ANN 找不到 | 索引和查询搜索参数 |
| 候选有正确段落，最终没选中 | 重排与去重策略 |
| 正确证据进入上下文却答错 | 上下文组织、指令与模型 |
| 答案正确，引用不支持 | 断言与来源绑定 |

## 稠密检索模型怎样学习相关性

双编码器分别编码查询与文档，通过训练让相关配对比不相关配对更接近。文档向量可以离线生成，在线查询只需编码一次，因此适合大规模候选召回。

负样本决定模型如何区分“相关但不是答案”的内容。太简单的负样本可能只教会主题分类；困难负样本可能提高细节辨别，也要避免把真实相关项误标为负。查询与文档编码的约定、池化和相似度应与训练一致。

Cross-encoder 将查询与候选联合读取，更适合精细重排，但无法预先为所有查询保存一个通用分数。召回与重排的两阶段结构是在覆盖、计算和延迟之间折中。原始依据：[DPR](https://arxiv.org/abs/2004.04906)、[Sentence-BERT](https://arxiv.org/abs/1908.10084)。

## 融合排序的机制

关键词与向量分数通常不在同一尺度。直接加权需要校准；RRF 按各路排名贡献分数，使在多个列表靠前的候选获得支持。

RRF 不依赖原始分数可比，却丢失分数间距。它也不能判断资料是否授权、是否有效或是否真的能回答问题；过滤与证据判断仍由其他步骤承担。某一路缺席的候选如何计分，需要有明确约定。

## 图索引、分区与压缩

HNSW 使用多层邻近图组织搜索，通过图上的逐步访问缩小候选，适合低延迟近似检索，但图连接和向量占用内存。搜索范围更大可能提高召回，也增加耗时。

IVF 类方法先按分区缩小搜索范围，再查所选分区；PQ 类压缩降低向量存储与距离计算字节量，但引入近似误差。索引选择取决于规模、更新、内存和召回要求，而不是只按一种算法流行度。

精确向量近邻、ANN 近邻和业务相关性是三层不同对象。索引几乎复现精确排序，也可能因为 Embedding 没学到目标关系而找不到答案。原始入口：[HNSW](https://arxiv.org/abs/1603.09320)、[Faiss 官方文档](https://github.com/facebookresearch/faiss/wiki)。

## 查询改写、拆分与多跳检索

短查询常缺少指代对象或时间条件，改写可以结合对话补全。但改写必须保留用户已确认的意图，不能凭模型猜测增加事实。

跨文档问题可能需要先找到实体或定义，再检索与之相关的另一条证据。多跳增加覆盖，也增加分支与错误传播。每跳应保留查询、来源和版本，最终检查证据链是否共同支持结论。

结构化条件适合交给元数据或数据库约束，而不是全部翻译成语义相似度。精确编号、日期和权限是检索系统中的硬条件。

## 上下文预算与长上下文模型

大窗口允许放更多候选，却不保证模型能排除干扰、发现冲突或使用远处细节。更完整的证据也可能增加成本，检索仍有选择价值。

上下文组织按必要条件与来源完整性打包，避免简单按分数截断。文档版本冲突需要显式解释；需要原文完整结构时可回读父段或原文件，而不强行在短片段中猜。
