# 18 · 推理引擎内部、容量与调度

[返回目录](../README.md) · [推理基础](09-inference-and-memory.md) · [下一章](19-retrieval-engineering.md)

## 首次处理与增量处理的计算差别

对普通稠密层，忽略偏置：Q/K/V/O 投影的矩阵乘法约为 `8 × B × T × d²` FLOPs，两矩阵 FFN 约为 `4 × B × T × d × d_ff`。这里按一次乘加计两个浮点操作。

全注意力的 QK 与 AV 两次乘法约为 `4 × B × T² × d`，但因果结构、高效实现、Mask 与实际算子会改变实际执行量。不能把整层计算都简化为 T²。

单步 Decode 只有一个新查询，但它读取历史。注意力部分约为 `4 × B × T × d`；FFN 仍需要处理每个新增 Token，权重也仍需被执行路径读取。

## 为什么小批次 Decode 常受带宽限制？

一次小批次矩阵乘法，巨大的权重矩阵可能只服务少量输入。算术强度，也就是「每读入一个字节做多少计算」，较低。

带宽约束不是固定速度保证。缓存复用、量化、并行分片、MoE、算子融合和实际有效带宽都会改变所需访问与耗时。应同时检查权重字节量、持续带宽和批次大小。

更大的批次可让同一权重为更多 Token 服务，提高算术强度。但同时增加 KV 读取、活跃序列容量和用户等待，需要结合目标负载测量。

## KV 容量应该按活跃 Token 管理

标准全注意力 K/V 头结构中，每条序列每个 Token 的状态字节量由下列关系定义：

```text
bytes_per_token = 2 × L × h_kv × d_h × bytes_per_value
```

其中 2 表示 K 与 V，L 是层数，h_kv 是 K/V 头数，d_h 是每头维度。长序列和短序列占用不同容量；滑窗或压缩状态结构需要按实际架构判断。

真实服务通常按活跃 Token、缓存块、输入/输出预留和最大序列长度进行准入控制。预留全部输出可能保守，按需增长又可能在中途耗尽空间，需要明确策略。

## 分块缓存与块表

将 KV 分为固定长度的块，逻辑序列通过块表指向物理缓存，不要求全部连续分配；相邻逻辑块可以位于不同物理地址。

尾块没有填满会造成内部浪费。更小的块降低尾部浪费，但增加块表大小、索引和管理开销。

共享前缀可让多条序列引用相同只读块；分支续写到部分共享块时，需要正确处理引用计数和写时复制。租户隔离、版本和前缀语义必须参与复用条件。

## Prefill 与 Decode 如何竞争资源？

一个非常长的输入可能占据较大计算时间，而正在流式输出的用户更关心下一 Token 是否及时到达。

- **长 Prefill 一次执行：**调度简单，但可能使 Decode 出现间隙。
- **Chunked Prefill：**将长输入分段，在步骤之间安排 Decode，降低阻塞；分块大小会影响算子效率与调度开销。
- **分离 Prefill/Decode：**分别优化设备或工作进程，但需要传输 KV 状态，并引入网络、路由和容量协调。

分离方案是否划算，要比较 KV 传输量和带宽。传输时延取决于状态字节量、有效带宽、协议和排队；短请求可能得不偿失。

## Prefix Cache 命中要怎样定义？

复用依据通常包含精确的 Token 前缀、模型权重与适配器版本、位置和缓存格式。有些运行时还依赖特定配置与块边界。

文字显示一样而 Token 不同，不能复用；使用了另一个 LoRA 适配器，也不能默认复用。检索内容经常变化时，固定系统指令可能命中，动态证据段则可能不命中。

测量缓存收益要报告命中 Token 数和省下的计算，不只报告请求命中比例。命中短前缀与长前缀的收益不同。

## 量化改变的是哪一部分？

线性量化常使用 scale 与 zero-point，将实数映射为有限整数。一个示意形式是：

```text
q = round(x / scale) + zero_point
x_approx = scale × (q - zero_point)
```

per-tensor、per-channel 和 per-group 使用不同粒度的 scale。更细粒度可能降低误差，但增加元数据和执行复杂度。权重量化、激活量化、KV 量化分别处理不同张量，不能互相推断。

权重存成 4-bit，不意味着所有乘法都直接以 4-bit 完成。某些算子边读取边反量化，再使用更高精度计算。速度还取决于设备与内核支持。

## 张量并行的通信账

张量并行常将投影矩阵按行或列拆分。层内需要在适当位置汇总或分发结果，否则各设备得到的只是部分输出。

如果把一个本来能在单设备运行的较小模型拆到多个网络较慢的设备，通信开销可能超过计算节省。评估应明确单机互联、跨机网络、TP 规模和每层通信频率。

副本数量主要改善总吞吐和可用性；TP/PP 主要解决单副本容量与计算分布。两者可以组合，但设计目标不同。

## 推测解码为什么需要概率校正？

草稿分布 q 提出候选 Token，目标分布 p 验证。在经典采样算法中，接受概率与 `min(1, p(token)/q(token))` 有关；拒绝时从修正后的剩余分布采样，避免直接把草稿偏差带进目标分布。

这不是简单地「草稿和目标选同一个就保留，否则换一个」。完整算法还处理连续候选、拒绝位置和额外目标采样。Greedy 情况又有自己的匹配规则。

粗略收益取决于一次验证能接受多少 Token，及草稿/验证成本。接受率很高但草稿很贵，也可能没有提升；低并发场景的收益不等于高负载吞吐收益。

## 性能行为与负载形态

先固定任务质量，再分开控制输入长度、输出长度、并发和到达速率。记录排队、TTFT、ITL、端到端延迟、输入/输出吞吐、缓存命中和拒绝率。

闭环压测在前一个请求完成后才发下一个，可能无法反映真实到达率下的排队累积。开放到达过程则需要控制持续负载，并观察是否进入不稳定排队。

Little 定律在稳定系统中给出 `平均在途请求数 = 平均到达率 × 平均停留时间`。它适合检查容量统计是否自洽，但不是峰值或 P99 的直接预测公式。

## KV 的回收、共享与抢占

完成、取消或失败的请求需要释放缓存引用；共享前缀需要引用计数或等价的生命周期管理，避免其他请求仍读取的块被覆盖。分支在共享尾块上写入时，还要保证隔离。

容量紧张时可以拒绝新请求、抢占已有请求、重算或卸载状态。重算节省暂存但增加计算，卸载保存状态但增加搬运，抢占改善某些优先请求却影响被暂停用户。这些是不同服务策略。

缓存命中需要同时看命中长度、占用容量和真正省下的工作。保留大量不再访问的长前缀会挤掉活跃任务，命中率高也可能总体效率低。

## 量化的质量与执行路径

量化误差受张量分布与粒度影响，异常大值可能使较粗的范围损失普通值精度。校准数据需要覆盖目标负载，权重与激活采用不同格式时要检查相应内核。

反量化、元数据访问、布局转换和不支持算子的回退都会消耗时间。权重字节量减少，在带宽受限场景可能有收益，在其他场景未必。同样要检查长输入、工具格式和目标领域的质量。

KV 量化减小请求状态，误差会进入历史读取与后续生成；不能只依据短样例证明长对话表现。量化是容量、数值与执行的联合选择。

## 推测解码与负载条件

推测方法通过一次目标验证处理多个候选，利用目标模型的并行计算。高接受率能减少串行步骤，但需要支付提议与验证成本。

低并发下能缩短单请求延迟，不代表高负载下总吞吐同样提高。目标计算已经充分利用时，额外草稿可能竞争资源。不同任务、温度和输出风格也会改变接受率。

采用分布保持的算法时，接受、拒绝与修正采样共同保证条件；直接跳过低置信度检查则不能继续声称保持原分布。原始依据：[Speculative Decoding](https://arxiv.org/abs/2211.17192)。

## 性能优化要保留质量语义

缓存布局、高效内核、编译和并行通常希望保持模型语义；量化、近似状态和某些解码策略则可能改变数值或输出分布。比较前先说明改变了哪一层。

引擎升级应关注输出与任务质量、容量、尾延迟和取消回收。只用固定短输入测得最高 tokens/s，会遗漏真实长度分布与过载行为。相关章节：[服务架构](10-serving-and-distributed.md)、[执行布局](16-transformer-implementation.md)。
