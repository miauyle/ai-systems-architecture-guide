# 16 · 从 Transformer 公式到可运行实现

[返回目录](../README.md) · [基础结构](04-transformer.md) · [下一章](17-training-engineering.md)

本章的目标是让你能跟踪一个真实前向程序中的每一笔计算，而不只是记住 Attention 的公式。配套代码：[transformer_numpy.py](../examples/transformer_numpy.py)。

## 1. 先规定模型，而不是先写框架调用

教学模型采用 Decoder-only、Pre-Norm、普通 MHA、GELU FFN、可学习的绝对位置向量。它不使用 RoPE、GQA 或量化；这些属于需要另行实现的变体。

| 配置 | 数值 | 含义 |
| --- | --- | --- |
| 词表 V | 32 | 最后输出 32 个候选分数 |
| 隐藏维度 d | 16 | 每个位置保留 16 个特征 |
| 注意力头 h | 4 | 每头维度 d_h = 4 |
| 层数 L | 2 | 每层包含注意力和 FFN |
| FFN 中间维度 | 32 | 先扩展再压回 16 维 |
| 最大长度 | 64 | 位置向量表的行数 |
| 计算精度 | float64 | 便于比较数值一致性，区别于常见部署精度 |

权重随机初始化，没有训练。这个模型用于验证计算机制，不能据此评价语言能力。归一化省略可学习的缩放与偏移，矩阵投影省略偏置，且不实现 Padding、Dropout 和自动微分。

## 2. 从整数到隐藏状态

输入 `[[1, 4, 8, 3, 7]]` 的形状为 `[1, 5]`。对每个 ID 从词向量表取一行，再加上对应位置向量，得到 `[1, 5, 16]`。

增量生成时，位置编号必须继续增长。若已经处理三个 Token，新增位置应从 3 开始。每次把位置重置为 0，会让缓存保存的历史位置语义与新查询不一致，即使缓存维度看起来完全正确。

## 3. 拆头为什么需要 reshape 加 transpose？

Q 投影后为 `[B, T, d]`，先 reshape 成 `[B, T, h, d_h]`，再交换时间维和头维，得到 `[B, h, T, d_h]`。

`reshape` 只是重新解释排列，`transpose` 才把头放到独立的批处理维上。直接 reshape 成 `[B, h, T, d_h]` 一般会把不同位置的数据分错，程序可能不报错，但计算含义已经变了。

本例每头的点积是 `[5, 4] @ [4, 5] → [5, 5]`。四个头并行，完整分数形状为 `[1, 4, 5, 5]`。

## 4. 沿哪个维度做 Softmax？

每个查询对应一行键分数，Softmax 应沿键位置，也就是最后一维。对每个查询，允许读取的所有键权重总和为 1。

若沿头维归一化，变成了不同头彼此竞争；若沿查询维归一化，变成了不同位置彼此竞争。维度一致并不能证明实现正确。

实现先减去每行最大值，再指数化。因果 Mask 用负无穷填入不允许的分数；本模型保证每一行至少有一个允许键，避免整行被屏蔽导致 `0/0` 或 NaN。

## 5. FFN 的「逐位置」是什么？

`[B, T, 16] @ [16, 32]` 得到 `[B, T, 32]`，经过 GELU，再乘 `[32, 16]` 得到 `[B, T, 16]`。

这一步不直接混合 T 维，因此 FFN 的权重在所有位置共享。它仍能使用上下文，因为输入隐藏状态已经经过注意力汇总。不要将「逐位置计算」理解为「只知道原始单个词」。

## 6. 因果注意力与缓存的完整形状

无缓存时，Q/K/V 的时间长度相同。缓存存在时，新 Q 只对应本次输入；K/V 则拼接历史和新增部分。

| 情况 | Q 的形状 | K/V 的形状 | 分数的形状 |
| --- | --- | --- | --- |
| 首次处理 5 个位置 | `[1, 4, 5, 4]` | `[1, 4, 5, 4]` | `[1, 4, 5, 5]` |
| 已有 3 个，新增 1 个 | `[1, 4, 1, 4]` | `[1, 4, 4, 4]` | `[1, 4, 1, 4]` |
| 已有 3 个，新增 2 个 | `[1, 4, 2, 4]` | `[1, 4, 5, 4]` | `[1, 4, 2, 5]` |

最后一种情况不能简单使用从左上角开始的 `2 × 5` 下三角 Mask。两个查询对应的是全局位置 3 和 4，正确允许关系为：

```text
键：       0  1  2  3  4
查询位置3  ✓  ✓  ✓  ✓  ×
查询位置4  ✓  ✓  ✓  ✓  ✓
```

这就是代码为什么根据全局 query/key positions 比较，而不是盲目创建一个普通三角矩阵。

## 7. 为什么缓存能得到相同结果？

因果网络中，旧位置的隐藏状态只依赖旧前缀。新增 Token 不会改变旧位置已经计算出的 K/V，因此可以复用。

等价性有条件：相同权重、位置机制、前缀、Mask 和计算模式；不能混入训练态 Dropout，也不能将不同请求的历史缓存接在一起。量化或算子差异可能引入额外数值误差。

## 8. 三个验证，比只检查形状更有用

```bash
python examples/transformer_numpy.py
```

程序验证：

1. **完整计算 vs 逐 Token 缓存计算：**所有位置的 logits 应接近。
2. **修改未来 Token：**前三个位置的 logits 不应变化。
3. **处理前缀后一次新增两个 Token：**结果应与完整计算的对应位置一致。

本次运行得到参数量 6,144、logits 形状 `(1, 5, 32)`、完整与缓存计算最大差约 `4.44e-16`；未来泄漏与分块续算最大差均为 0。微小浮点差可能随 NumPy 和 BLAS 实现变化。

这三个性质分别检查缓存等价性、因果性和位置偏移，能发现一些不会触发形状错误的实现问题。

## 9. 从教学实现到生产实现还差什么？

| 教学实现 | 生产中需要进一步处理 |
| --- | --- |
| `concatenate` 不断复制缓存 | 预分配、分块缓存、块表与回收 |
| 显式分数矩阵 | 融合算子和高效注意力 |
| 同长度批次 | 不等长请求、Padding 或变长算子 |
| float64 | 精度选择、数值稳定、量化校准 |
| 普通矩阵乘法 | GPU kernel、通信与图编译 |
| 随机模型 | 匹配权重、Tokenizer、配置和任务评估 |

优化之前先保留一个可信的参考实现，再验证优化后的输出和任务质量。速度快但语义错的算子没有工程价值。

## 练习与判断依据

- 把 `split_heads` 的 transpose 去掉，先预测会出现什么问题，再观察等价性检查是否能暴露它。
- 把新增 Token 的位置编号重置为 0，观察缓存等价性失败。
- 将 Mask 设为全部可见，观察修改未来 Token 后的早期输出变化。
- 用 `parameter_count()` 对照每个权重矩阵，不将位置表或输出头漏算。

运行前请保留原示例。实验失败时写清是数值误差、语义变化还是实现错误，而不只写「结果不同」。
