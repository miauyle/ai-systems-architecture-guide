# 27 · AI 计算基础设施与数据路径

## 模型计算依赖一条完整数据路径

加速器执行矩阵、归约和逐元素操作，但计算前要准备数据，计算中要访问状态与通信，计算后要取回结果或提交检查点。设备峰值算力只给某些算术的上限，不代表整个任务的完成速度。

系统分析先定位对象在哪、谁读写、何时就绪，以及哪个等待不能被其他工作隐藏。训练的关键路径可能是输入、反向或梯度归约；推理可能是排队、权重访问、KV 读取或 TP 通信，瓶颈会随批次与长度变化。

## 状态在不同层级间怎样移动

| 层级 | 主要对象与操作 | 成本与约束 |
| --- | --- | --- |
| 持久存储 | 数据集、权重和检查点的读写 | 吞吐、请求延迟、版本与完整提交 |
| 主机内存与 CPU | 解析、解码、Tokenize、批次和元数据准备 | 计算、复制、内存容量、NUMA 与 worker 调度 |
| 主机—设备通道 | 输入、权重、卸载状态的传输 | 字节量、通道带宽、缓冲和完成依赖 |
| GPU HBM | 常驻权重、KV、激活、工作区 | 容量、带宽、分配与对象生命周期 |
| 片上缓存/共享内存/寄存器 | 内核局部块与累积状态 | 数据复用、资源占用和同时运行能力 |
| 设备互联与网络 | 梯度、激活、专家 Token、迁移 KV | 拓扑、通信模式、时延、拥塞和同步 |

CPU 不会为每个 GPU 算术指令逐次指挥，它提交内核和传输工作，设备再调度线程。内核将 HBM 中的数据搬入更近的资源，复用后写回。融合和分块减少中间读写，具体 Attention 路径见[第 16 章](16-transformer-implementation.md)。

缓存或卸载改变访问层级，不创造无限容量。状态从 HBM 移到主机后，占用下降，下一次使用却需要传回或走更慢访问路径；收益取决于复用和空闲时间。

## 一个训练批次怎样与下一批重叠

存储中的样本先被读取、解压和预处理，再形成主机批次，搬到设备，进入前向/反向。可用两个或更多缓冲让 CPU 准备下一批时 GPU 计算当前批，但每一阶段都必须知道缓冲何时可读、何时可重用。

Pinned memory 让主机缓冲适合某些 DMA 和异步传输路径，代价是占用难回收的主机资源。对可异步的路径，CPU 提交完成不代表传输完成；设备计算要等待相应事件，主机也不能提前改写仍在被读取的源缓冲。

不同 stream 可以表达独立工作的并行与事件依赖，但不保证硬件一定重叠：还取决于复制引擎、通道、计算资源与隐式同步。把传输与计算放进同一有序队列，或每次调用后全设备同步，可能使看似“异步”的代码仍然串行。

预取太少会让设备饿死，太多增加内存、无效读取和恢复复杂性。worker 的随机/分片策略要避免重复漏样本，并与训练数据进度一致。GPU 等待不一定是磁盘慢，也可能是解析、CPU 调度或元数据准备。

## 算术强度怎样解释 Prefill 与 Decode 差异

硬件提供算力、指定内存层级的带宽和互联上限，实际访存字节还取决于缓存与布局。算术强度、Roofline 和 Prefill/Decode 随负载变化的瓶颈分析统一见[第 30 章](30-ai-systems-performance.md)；本章跟踪对象经过哪条物理路径。GPU utilization 与有效工作的观测区别见[第 31 章](31-ai-systems-observability-and-debugging.md)。

## 集体通信究竟交换什么

rank 是通信组中的逻辑参与者，不必与机器编号相同。各参与者需使用匹配的元素解释、通信顺序和操作；只在部分 rank 调用同一个 collective 可能挂起，而不是“让其他卡稍后补上”。

| 操作 | 输入与输出关系 | AI 系统中的用途 |
| --- | --- | --- |
| all-reduce | 对所有 rank 对应元素做归约，每个 rank 获得完整结果 | DP 梯度汇总、TP 局部贡献相加 |
| all-gather | 收集各 rank 的不同片段，每个 rank 得到按约定顺序拼接的完整数据 | 分片参数在计算前取回 |
| reduce-scatter | 对完整对应贡献归约，再将结果不同片段交给各 rank | 分片梯度交给其所有者 |
| all-to-all | 每个 rank 向不同目的地发不同数据，各目的地接收自己的集合 | Token 到专家的路由与结果返回 |
| 点对点发送/接收 | 某源向某目标传一段数据 | PP 阶段激活及反向梯度 |

all-gather 的拼接不等于 all-reduce 的求和。all-to-all 可以因路由产生不等量负载，变长路由还需交换长度、偏移与索引，返回时恢复原 Token 顺序。

一种环形 all-reduce 实现先把缓冲分片，各轮将片段传给邻居并累加，完成 reduce-scatter 后再传播归约完成的片段，形成 all-gather。它说明为什么归约可分块流水化；实际库可按消息和拓扑采用其他算法，不能把一种环形路径当作通用协议。

DDP 的 bucket 可将通信与反向重叠，FSDP 的预取可隐藏参数 gather，但重叠增加同时存活的缓冲，且争用 HBM/互联。TP 小批次的频繁短消息更敏感于时延；跨机带宽、慢 rank 与专家热点都可能限制整组。依据：[NCCL 集体操作](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/collectives.html)。

## RDMA 与直接路径省掉哪一次复制

传统网络路径可能经过主机网络栈和内存中转。RDMA 提供受管理的远端内存访问，减少部分 CPU 处理/复制，需要内存注册、设备和传输支持；它不替代应用的授权、对象版本或成功提交语义。

GPUDirect RDMA 可在支持组合中让网卡等设备直接访问 GPU 内存，省去部分主机中转。收到网络完成信号与 GPU 安全可用数据的关系仍需按驱动/同步合同处理。GPUDirect Storage 面向存储到 GPU 的路径，支持条件和收益不能由前者推断。

“零拷贝”要指明省掉哪次复制，数据仍需跨通道搬运，格式转换、注册、同步与访问控制仍有成本。训练输入、状态通信与模型加载都需要沿实际路径判断收益，不能由一个技术名推断全链路效果。

## 冷启动为什么不只是下载权重

加载路径需要将存储格式转换为执行格式，再把参数分片送到设备；节点文件命中不代表 HBM 中已经就绪，转换还可能造成双份驻留峰值。完整冷启动与多副本加载生命周期由[第 29 章](29-ai-platform-and-cluster-scheduling.md)主责，本章只解释数据可达性、复制和缓冲依赖。

## 异步检查点怎样保持可恢复

Checkpoint staging 与后台写入占主机/设备缓冲、传输和共享 I/O；前台继续执行前必须保护固定快照，缓冲复用要等待实际消费者完成。一致更新点、持久提交、分片失败与 reshard 的主解释见[第 17 章](17-training-engineering.md)，不能从一次复制完成推断已可恢复。
