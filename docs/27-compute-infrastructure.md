# 27 · AI 计算基础设施与数据路径

[知识地图](00-learning-roadmap.md) · [训练系统](17-training-engineering.md) · [推理引擎](18-inference-engineering.md)

## 算力是系统中的一项资源

神经网络大量使用矩阵乘法与归约，GPU 等加速器通过并行执行提高吞吐。但真实任务还要读取数据、解码、搬运、通信、调度与输出。峰值计算能力只描述某种运算条件下的上限，不能直接预测整个系统速度。

一次训练迭代可能受输入供给、前向反向、梯度通信或检查点限制；一次推理可能受排队、权重读取、长上下文、跨卡通信或工具访问限制。优化要先确定哪个环节位于当前关键路径。

## 主机、设备和存储的层级

| 层级 | 主要对象 | 系统关注点 |
| --- | --- | --- |
| 持久存储 | 数据集、权重、检查点、原始文档 | 吞吐、延迟、并发、版本与持久性 |
| CPU 与主机内存 | 解析、解码、请求处理、预取 | 单核/多核能力、缓冲、内存与 NUMA |
| 主机到设备通道 | 批次、加载权重、卸载状态 | 搬运字节量、异步与计算重叠 |
| GPU HBM | 权重、KV、激活、工作区 | 容量、带宽与碎片 |
| 片上资源 | 寄存器、共享内存、缓存 | 内核的数据复用与并发 |
| 设备互联与网络 | 梯度、激活、专家路由、KV | 带宽、时延、拓扑与拥塞 |

缓存降低某些层级的访问成本，不能创造无限容量。状态从 HBM 卸载到主机或存储后，占用下降，访问与调度成本却上升。是否划算取决于复用频率与设备空闲状况。

## 算术强度与执行瓶颈

算术强度描述读取一定字节完成多少运算。矩阵乘法通过复用数据可以有较高强度，少量 Token 的大权重计算则可能频繁读取权重而复用不足。

Roofline 思路将算力上限与带宽上限联系起来：计算量很大不一定计算受限，低强度任务即使换更高峰值算力也可能没有对应加速。归约、内核启动和同步还会形成不同限制。

较大批次提高权重复用，但增加排队和 KV 占用。长 Prefill 通常有更多并行计算，小批次 Decode 常受带宽影响；这些是常见倾向，必须与具体架构和负载一起判断。

## GPU 利用率不能单独代表效率

设备“忙”可能在执行低效率内核、通信或重复计算。显存用满也可能来自保守预留，而非高吞吐。应将阶段耗时、有效 Token、服务目标与硬件计数联系起来。

训练中的模型 FLOPs 利用率依赖计算量定义，重计算等实际工作与模型理论工作不能混为一谈。推理中的 tokens/s 还需要明确输入输出长度、并发与质量约束。

## 训练输入路径

数据从存储进入主机，经解压、解析和预处理，形成批次，再搬入设备。预取和异步传输可以与计算重叠，但会使用额外内存，也可能读取最后并未消费的数据。

固定数据集的分片顺序影响缓存命中与随机性；多 worker 处理要避免重复与漏样本；主机上的重预处理可能比设备传输更慢。不能仅因训练等待就默认需要更快磁盘。

Pinned memory 让主机缓冲适合某些 DMA 和异步传输路径，但会占用不可轻易回收的主机资源。它不会使 CPU 内存变成 GPU HBM，也不是零成本的“零拷贝”。

## 通信与拓扑

数据并行通常归约梯度，张量并行在层内交换部分结果，流水线并行传递阶段激活，专家并行发送 Token 到对应专家。它们产生不同频率、大小和目的地的通信。

All-reduce、all-gather、reduce-scatter 和 all-to-all 是不同的集体通信模式。带宽足够但时延高的网络，仍可能损害频繁小通信；专家路由不均还会使少数设备成为热点。

单机高速互联和跨机网络的成本不同。并行分组应尽量与拓扑匹配；增加设备既减少单设备工作，也增加通信和同步。慢节点可以拉长整个同步训练步骤。

## RDMA、直接数据路径与“零拷贝”

RDMA 提供远端内存访问机制，可以减少传统网络数据路径中的部分 CPU 和复制开销，但需要相应网卡、内存注册、传输协议和资源管理。它不自动改变对象存储或应用协议的语义。

GPUDirect RDMA 关注支持条件下网络设备与 GPU 内存之间的数据路径；GPUDirect Storage 关注存储与 GPU 的直接访问路径。协议支持、文件系统、驱动、平台与具体工作负载决定可用性和收益。

“零拷贝”要指明省掉的是哪次复制，不能理解为数据无需搬运。GPU 仍要读到数据，内存注册、同步、格式转换和访问控制仍有成本。存储、网络与计算优化见各自官方资料，不由一个技术名推断全链路效果。

## 权重加载与冷启动

冷启动可能包含权重下载、磁盘读取、反序列化、分片合并、量化格式处理、设备加载、通信初始化、编译与预热。模型服务扩容慢可能来自多个步骤。

节点缓存和预热可以降低重复工作，但模型版本多时会竞争存储和显存。多副本同时启动还可能冲击共享存储与网络，扩容策略需要考虑供给链而不只是创建进程。

## 检查点的数据路径

同步写检查点容易暂停训练；异步写先保存一致状态，再在后台持久化，可以缩短部分阻塞，却需要主机缓冲与可靠提交。

检查点完成的含义应区分内存快照、数据上传和可恢复的持久提交。后台写失败不能被“前台继续训练”掩盖；删除旧检查点前，需要知道新版本已经完整可用。

## 调度、隔离与服务容量

集群调度分配设备与拓扑，模型引擎调度 Token 和缓存，应用调度任务与工具。它们是三个不同控制层。Kubernetes 可以管理进程与资源，不能自动替代引擎内部的 KV 和批次调度。

多租户共享要处理优先级、限额、长请求、公平性与取消。设备切分或进程隔离可以限制资源，仍需考虑带宽、网络和数据缓存的竞争。服务容量由目标负载下的质量、尾延迟和错误率定义，而非单个峰值指标。
